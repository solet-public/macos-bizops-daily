# UTC Time-Convention Policy — Canonical Storage, Naive-Is-A-Defect, Display-Local-Only

Article Layer: 1
Article Role: platform_constraint
Article Tags: planning-stage:always, evidence-category:constraint, evidence-category:incident, domain:platform-operations, domain:time-handling, consumer_profile:both

Embedding Description: The platform's UTC time-convention policy — every stored, evaluated, and compared timestamp is UTC-canonical, a naive (offset-less) datetime is a defect class in this codebase, any local-clock display goes through an explicit IANA timezone field and never substitutes for the canonical value, and two measured 2026-08-16 incidents (a scheduler cron trigger silently evaluating in host local time, a peer-registry freshness column read back offset-naive and compared against an aware clock) show what a naive-vs-aware mismatch actually does at runtime: it does not raise, it silently produces the wrong answer in one of two opposite directions depending on which side is wrong.

**When you need this**: writing or reviewing any code that creates a schedule, cron trigger, or timer; reading a `DATETIME`-typed state column back into a comparison, subtraction, or freshness check; deciding whether a "local time" display value is safe to also use for logic; calibrating a naive-datetime defect on a codebase you didn't write the storage layer for.

## The policy

1. **UTC is the only canonical basis.** Every timestamp that is stored, evaluated, compared, or transmitted between processes is UTC. There is no second canonical clock.
2. **A naive (offset-less) `datetime` value is a defect, not a style choice.** A value with `tzinfo is None` carries no information about what clock produced it — code that constructs one implicitly borrows whatever timezone the host process happens to be running in, which is invisible at the call site and can differ between the machine that stores a value and the machine (or the same machine, months later, on different infrastructure) that reads it back.
3. **Local time is display-only, and it goes through an explicit IANA timezone identifier — never a bare `datetime.now()`.** When a human-facing string needs to show "your local time," compute it from the canonical UTC value plus an explicit, named zone (e.g. `zoneinfo.ZoneInfo("America/Vancouver")`, or the host's resolved zone name carried alongside the string it labels), and keep the canonical UTC value as the thing any other code actually reasons about. A local-time string that also gets fed into a comparison or a scheduler is not display — it is the defect this policy exists to prevent.
4. **A naive value read back from storage is coerced to a known basis at the read boundary, once, before it does anything else.** This codebase's state layer stores `DATETIME` columns as `timestamp without time zone` — every stored cell reads back offset-naive, by a platform-wide storage convention that a naive cell means UTC wall-clock. That convention is not visible at the read site unless the reader coerces explicitly. Two coercion conventions are in active use and both are correct in isolation: coerce to naive-UTC (`ananta/src/ananta/core/domain/timestamps.py::to_naive_utc`) or coerce to aware-UTC (the `_parse_iso` pattern in `ananta/src/ananta/llm/agent_messaging/service.py` and mirrored in `plugins/agent_messaging_plugin/src/agent_messaging_plugin/session_sweep.py`). Pick one per call site and be consistent within it — mixing an object coerced one way against one coerced the other way raises `TypeError` immediately on comparison, which is the SAFE failure mode: loud, not silent. A comparison that instead trades a naive value against an aware one directly (no coercion at all) is where the real damage happens, and that is what both worked examples below did.

## Why this is a defect class, not a hypothetical

A naive-vs-aware mismatch does not fail loudly by default. Python only raises `TypeError` when you compare a naive `datetime` directly to an aware one; if code instead builds two ordinary naive values from two different implicit clocks (one from the host's local timezone, one already stored as UTC-labeled-but-naive) and compares or subtracts them, the arithmetic succeeds and returns a wrong number silently. Which direction it's wrong in depends on the sign of the offset and which side of the comparison carries it — the two incidents below show both directions from the same underlying defect class, on the same day, in unrelated subsystems.

## Worked example 1 — cron triggers evaluating in host local time (2026-08-16)

`plugins/default_scheduling_plugin/src/default_scheduling_plugin/scheduling/scheduler_manager.py`'s `SchedulerManager` builds its APScheduler `BackgroundScheduler` with `timezone=datetime.UTC` — the scheduler object itself is correctly configured. But `add_cron_job` called `CronTrigger.from_crontab(cron_expression)` with no `timezone` keyword argument. APScheduler's `CronTrigger.__init__` resolves an unset `timezone` to `get_localzone()` — the HOST's local timezone — **at trigger-construction time**, and never consults the `BackgroundScheduler`'s own configured timezone at all, despite `from_crontab`'s own docstring claiming an unset timezone "defaults to scheduler timezone." The plugin's own knowledge-base reference article stated "All cron expressions use UTC timezone" — the documentation was itself part of the defect, describing intended behavior that the code did not implement.

Reproduced directly against the installed dependency: `CronTrigger.from_crontab('30 7 * * *').timezone` resolved to `America/Vancouver`, a −25,200-second offset from UTC on the affected host — every recurring schedule on that deployment was evaluating seven hours off from what its cron expression and its owning code's documentation both claimed. This was silent and platform-wide: every recurring cron-based schedule on the affected deployment carried this defect from the moment the scheduler's UTC-timezone configuration was written, discovered only when one specific schedule's unrelated failure (see the companion `ActionExecutor`-initialization defect, recorded in the checkout-local measurement file workbench/2026-08-16_lane_utc_scheduler_phase1_measurement_lane_utc_scheduler.md) got investigated for a different reason and the investigation happened to also read the trigger's actual resolved timezone.

Fix: pass `timezone=datetime.UTC` explicitly at the `CronTrigger.from_crontab` call site. Landed 2026-08-16, commit `497c41ec2` / merge `f420e5372`, with a red-first smoke (`plugins/default_scheduling_plugin/tests/cron_utc_timezone_smoke.py`) that pins a fixed, deliberately non-UTC `get_localzone()` return value rather than the test host's own zone — so the smoke stays meaningful on a host whose local zone happens to already be UTC, where the naive version of this test would pass for the wrong reason and silently stop covering the defect.

## Worked example 2 — a UTC-naive registry column and the freshness guard it nearly disabled

A peer-registry state column (`peer_list`'s `updated_at`) is stored UTC-naive, per this platform's general `DATETIME` storage convention (see policy point 4). A freshness/staleness guard needed to compute how old a registry row was, and the obvious implementation — parse the stored string, subtract it from a naive `datetime.now()` — would have been off by the full UTC offset (25,200 seconds, measured 2026-08-16, the same magnitude as worked example 1, independently confirming the host's actual local-UTC skew), in one of two directions depending on which side of the subtraction carried the error:

- If the naive `now()` read as "later" than the true UTC-basis stored value, every computed age comes out **negative** — the guard never trips, and a dead registry row is treated as fresh forever (fails open onto a stale/dead identity).
- If the sign flipped the other way, every computed age comes out **enormous** — the guard trips on every row, including genuinely live ones, and the mechanism that exists to prevent operating on dead identities instead reports nothing as ever fresh (fails closed, defeating the very check it implements).

Neither direction raises an exception. Both are silent, and both are worse than no guard at all, because a guard that always says "fresh" or always says "stale" reads as working while doing the opposite of its job.

The landed fix (`plugins/github_midwife_plugin/claude_plugin/coordination-hooks/hooks/rotation_due_watch.py::_registry_row_is_fresh`) coerces the stored value to aware UTC at the read boundary (`stamp.replace(tzinfo=UTC)` when `stamp.tzinfo is None`) and compares it against `datetime.now(UTC)` — aware-vs-aware on both sides — then treats a wildly negative computed age as a clock/timezone fault to be logged and skipped, rather than trusted as either "very fresh" or "very stale." This is the pattern worth copying: coerce once, at the boundary, to a named basis; treat an implausible result as evidence the coercion itself needs investigating, not as a legitimate extreme value.

## What to do when you touch a `DATETIME` column or a cron/timer primitive

- If you are constructing a comparison, a subtraction, or an age/freshness check against ANY value that came from storage, a cron library, or another process: confirm both sides are the same basis (naive-UTC-vs-naive-UTC, or aware-UTC-vs-aware-UTC) before the comparison runs, not after a bug report.
- If you are calling a third-party scheduling/cron library (as worked example 1 shows), do not trust that a library-level "scheduler timezone" setting propagates to every object the library constructs — verify the actual resolved timezone on the object you end up with, the way the smoke test for worked example 1 does, rather than trusting the surrounding configuration or the library's own docstring.
- If a value is genuinely for human display only, compute it from the canonical UTC value plus an explicit IANA zone, and do not let that display value flow into any later comparison or scheduling decision — the three-way duplicated (but correct) pattern in `ananta/src/ananta/core/actions/action_queue_poller.py`, `ananta/src/ananta/core/services/compilation_context_builder.py`, and `ananta/src/ananta/services/inference_service/transaction.py` (`now_utc = datetime.now(UTC)` shipped as the canonical value, `now_local = datetime.now()` used only inside `strftime` calls with an explicit timezone name alongside) is the reference shape for this.
- A `TypeError` from comparing a naive and an aware value directly is not a bug to silence with a blanket coercion — it is usually the loud failure mode surfacing a real basis mismatch before it becomes a silent one. Investigate which side is wrong rather than reaching for `.replace(tzinfo=...)` on whichever side raised.
